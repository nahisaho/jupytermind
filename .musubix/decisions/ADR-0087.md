# ADR-0087: Describe phase handlers in a machine-readable manifest and verify pinned sibling skills at startup

## Context / 背景
`DES-AISCI-015` (`REQ-AISCI-023`, `CHANGE-001`) must prove that every phase
handler is importable and that every sibling skill dependency named by the
design is actually available at the pinned version before dispatch begins.
The design trade-off is whether to make that topology explicit in one
manifest, or to infer it indirectly from code structure and runtime calls.

## Decision / 決定
The authoritative package map is `.github/skills/ai-scientist/manifest.json`,
where each phase declares `modulePath`, `functionName`, and
`skillDependencies`. Most phases use a list of dependencies; `peer-review`
alone uses the stricter `{ja, en}` mapping because its downstream skill
depends on persisted manuscript language. `load_phase_manifest(...)`
validates the entry shape, rejects missing handler coordinates, rejects
malformed `peer-review` dependency payloads, and imports every declared
handler to ensure it is callable.

Startup verification then compares the declared dependencies against a
repository-local registry built by `scan_repo_skill_registry()`, which reads
installed skill identifiers from `.github/skills/*/SKILL.md` and their
vendored versions from `.github/skills/VENDORED.md`. `verify_manifest_against_registry(...)`
requires exact `skillId`/`version` matches before any phase is dispatched.
This makes the handler/dependency topology explicit and checkable against
whatever skill files are physically present in the repository checkout.

**Resolved scope note** (originally a known limitation, narrowed by
CHANGE-020 per jupytermind#65): `DES-AISCI-015`'s requirement/design text
previously said verification must run against "the host Copilot CLI's
installed skill registry," while `scan_repo_skill_registry()` has always
only scanned this repository's own `.github/skills/` tree. Rather than
building live host-registry introspection (judged disproportionate scope
for this packaging verifier), `REQ-AISCI-023`'s acceptance text and
`DES-AISCI-015`'s Responsibilities/Constraints were corrected to explicitly
name the repository-declared skill registry as the verification authority,
matching what `scan_repo_skill_registry()` has always actually checked.
This is a specification correction, not a behavior change: no source code
changed. A host CLI running a stale/version-skewed skill relative to this
repository's `VENDORED.md` is out of scope for this verifier and must be
caught by other means (e.g. the host CLI's own install/update tooling).

## Rejected alternatives / 却下した代替案
- **Encoding the phase-to-handler mapping directly in Python code and skipping a manifest file**: rejected — the packaging contract itself is part of the skill surface, and a manifest gives both humans and tooling one inspectable source of truth without importing orchestration code to discover it.
- **Inferring sibling-skill dependencies by scanning handler source imports or invoker calls**: rejected — those call sites do not encode version pinning reliably, and peer-review's language-keyed dependency structure would be far less explicit.
- **Verifying handler importability and registry presence only when a phase is first invoked**: rejected — that would defer packaging defects into user-visible runtime failures instead of failing startup deterministically when the installation is incomplete.

## Consequences / 結果
Future phases or dependency-pin changes must update the manifest and remain
discoverable by startup verification before dispatch is allowed. Covered by
the acceptance tests in `tests/test_ai_scientist_skill_packaging.py`.
