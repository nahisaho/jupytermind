# ADR-0111: Slug-verified ancestor-directory discovery (not a marker file, mandatory env var, or basename-only match) for cross-process project-root stability

## Context / 背景
REQ-AIDS-044 (DES-AIDS-032) anchored `resolve_project`'s default
`projects_root` to the process's working directory captured once at module
import time, fixing the original single-process `os.chdir`-drift bug
(GitHub #15). GitHub #72 reports a related but distinct regression: in a
Jupyter MCP setup with multiple kernels/processes, a second process can be
started (or re-imports the module for the first time) with its own
import-time cwd already sitting inside an existing project's own
`projects/<slug>/notebooks` directory — for example because the notebook
server or kernel was launched from that directory. DES-AIDS-032's anchor is
correct but process-local: it has no way to know that another, already
existing `projects/<slug>` tree is sitting a few directories above it,
and recomputes `<that notebooks dir>/projects` as its own default root,
silently recreating a nested `projects/<slug>/notebooks/projects/<slug>`
tree instead of reusing the original one.

A real fix needs the new process to notice, without any explicit
coordination from the user or the original process, that it is already
"inside" an existing project tree — and to do so without introducing new
false positives against unrelated directories that merely happen to share
the name `projects`.

## Decision / 決定
Add a slug-verified ancestor-directory discovery step (DES-AIDS-093) to
`_default_projects_root()`, now threading the requested project `name`
through to it, evaluated only when `AI_DATA_SCIENTIST_PROJECTS_ROOT` is
unset: walk the import-time `_IMPORT_TIME_CWD` and every ancestor
(including it itself) and return the nearest candidate directory `A` such
that `A.name == "projects"` **and** `(A / name).is_dir()` — the candidate
must not merely be named `projects`, it must already contain a
subdirectory matching the *specific project name being resolved*. If no
ancestor satisfies both conditions, fall back unchanged to DES-AIDS-032's
existing `<import-time cwd>/projects` default.

This is deliberately self-healing and stateless: it requires no new
persisted file, no new environment variable that must be propagated to
every kernel, and no change to how a project is originally created. It
works precisely in the concrete failure mode reported in #72 (a new
process's cwd already lies within an existing `projects/<slug>/...` tree
for the project actually being resolved) and is a strict no-op everywhere
else — including the directory-name collisions discussed below — so it
cannot regress any existing single-process behavior covered by
REQ-AIDS-044's tests.

An initial design (reviewed and revised before this ADR reached its
current form) matched only the ancestor's basename (`A.name == "projects"`),
without verifying that it actually contained the requested project. Two
rounds of rubber-duck review found that basename-only matching produces
false positives in several realistic layouts, not just one narrow
self-collision case:

- A project whose own slug is literally `"projects"` creates a tree shaped
  `<root: .../projects>/<slug: projects>/notebooks`; the *nearest* ancestor
  literally named `"projects"` is then the slug directory, not the true
  root one level above it.
- A developer's personal workspace convention of cloning repositories
  under a directory literally named `~/projects` (e.g.
  `~/projects/myrepo/projects/<slug>/notebooks`, before that project's
  `projects/<slug>` tree even exists yet) would, under basename-only
  matching, either correctly resolve to the nearer, intended root (if
  "nearest" is used) or incorrectly jump to the unrelated `~/projects`
  workspace directory (if "outermost" is used) — but even "nearest"
  basename-only matching cannot by itself distinguish an ancestor that is
  the module's *own* root from one that is merely named the same thing.
- A pre-existing, unrelated nested directory that happens to be named
  `projects` (for example another project's own generated-output
  subdirectory) could be misidentified as this project's root purely by
  virtue of sharing the name.

Requiring `(A / name).is_dir()` — i.e., that the candidate ancestor already
contains a subdirectory matching the *specific* project name being
resolved, not just any `projects`-named ancestor — resolves all of these
at once: it ties the discovery decision to the one piece of information
that genuinely distinguishes "this is the project tree I am looking for"
from "this directory happens to be named `projects`." Under this rule, a
project whose own slug is `"projects"` also round-trips correctly without
any special-cased restriction: the inner `<root>/projects` slug-directory
does not itself contain a further `projects` subdirectory (so it fails the
containment test and is skipped), while the true outer root does contain
`projects` (the slug) as a child (so it is correctly selected). No project
slug needs to be reserved or restricted by this change.

The requirement (REQ-AIDS-093) explicitly limits its guarantee to the case
where the new process's cwd is already inside a `projects/<slug>` tree for
the project being resolved, rather than promising to solve every possible
multi-kernel topology (e.g., a second kernel started in a wholly unrelated
directory with no pre-existing tree for that project at all).

## Rejected alternatives / 却下した代替案
**Persisted marker/config file written at project-creation time** (e.g.
`projects/<slug>/.ai-data-scientist-root` or a repo-root `.ai-data-scientist.json`
naming the canonical root): would also solve the #72 scenario, and would
additionally help the "unrelated directory" case if the marker were
discovered via a broader upward search. Rejected for this change because it
requires writing and maintaining a new on-disk artifact that must survive
project renames/moves, adds a new failure mode (stale/incorrect marker
pointing at a deleted project), and is strictly more machinery than the
reported defect requires. Left as a candidate for a future change if a
broader cross-process guarantee is later required.

**Mandatory `AI_DATA_SCIENTIST_PROJECTS_ROOT` for every kernel/process**:
already available today and already takes precedence per DES-AIDS-032;
rejected as the *sole* fix because it requires every Jupyter kernel's
launch configuration to be updated with an absolute path, which is exactly
the manual coordination burden #72's reporter is trying to avoid in a
multi-kernel MCP session — the point of REQ-AIDS-093 is to make the common
case self-healing without requiring that configuration.

**Basename-only ancestor matching** (`A.name == "projects"` with no
containment check): the initial design; superseded for the reasons
detailed in the Decision above — it cannot distinguish the module's own
root from an unrelated or coincidentally-named `projects` directory, and
introduces a genuine self-collision when a project's own slug is
`"projects"`.

**Reserving `"projects"` as a disallowed project slug** (considered as a
narrower fix for just the self-collision case, while keeping basename-only
matching otherwise): rejected in favor of the slug-containment check
because it only closes the one self-referential collision and leaves the
broader basename-only false-positive risk (unrelated nested `projects`
directories, personal `~/projects` workspaces) unresolved, whereas
requiring `(A / name).is_dir()` closes all of these simultaneously without
restricting the set of valid project names at all.

**Picking the outermost (filesystem-root-ward) ancestor named `"projects"`
instead of the nearest one**: rejected because it breaks a more common
real-world layout than it fixes — a developer's personal workspace
directory literally named `projects` (e.g. `~/projects/myrepo/...`) sitting
above the module's own `<repo>/projects` root would be incorrectly
preferred over the nearer, correct root. The slug-containment check makes
this moot: whichever ordering is used, only an ancestor that actually
contains the requested project's slug can match, so "nearest" is both
sufficient and unambiguous.

**Heuristically disambiguating via sibling directory contents** (e.g.,
requiring a `notebooks`/`data` child, or checking that the parent is not
itself also named `projects`): rejected as needlessly fragile and
incomplete compared to directly checking for the one thing that actually
matters — whether this specific project's slug directory already exists
beneath the candidate.

**Environment-variable auto-propagation via a parent-process handshake**
(e.g., the original process writing its root into a shared location that
child kernels inherit): rejected as out of scope — Jupyter kernel processes
are not reliably parent/child of the originating process in every
deployment (remote kernels, kernel gateways), so no such handshake can be
assumed to exist.

## Consequences / 結果
- `_default_projects_root()` gains a `name` parameter and one additional,
  strictly additive discovery step; existing callers and tests for
  REQ-AIDS-044 are unaffected because the new step only changes behavior
  when cwd is already inside a `projects`-named ancestor that also
  contains the requested project's slug.
- REQ-AIDS-093's acceptance criteria are scoped to exactly this guarantee;
  a kernel started in a directory with no such ancestor is explicitly out
  of scope and continues to rely on `AI_DATA_SCIENTIST_PROJECTS_ROOT` or on
  being co-located with the original process's working directory,
  unchanged from today.
- No project slug is reserved or restricted by this change; `"projects"`
  remains a fully valid project name, verified to round-trip correctly
  under the slug-containment rule.
- If a future change needs the broader "any kernel, any directory, even
  before the project tree exists" guarantee, it should revisit the
  rejected marker-file alternative above as a separate, explicitly-scoped
  change rather than overloading this one.
