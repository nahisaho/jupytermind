# ADR-0126: Compute REQ-AIDS-116's graph connectivity/centrality analysis with `scipy.sparse.csgraph` (already available transitively via the existing `scipy` dependency), not by adding `networkx` as a new dependency

## Context / 背景
REQ-AIDS-116 adds `ai_data_scientist.network_analysis.analyze_network(
adjacency_matrix)`, computing connected components, per-node degree,
all-pairs shortest paths, and closeness centrality for an unweighted
undirected graph. The most commonly reached-for Python library for this
class of problem is `networkx`, which offers a large, graph-theory-
oriented API (`nx.connected_components`, `nx.closeness_centrality`,
etc.) and is not currently a dependency of this project. `scipy`,
however, is already a root `pyproject.toml` dependency
(`scipy>=1.11`) used throughout `ai_data_scientist`, and its
`scipy.sparse.csgraph` submodule already provides
`connected_components` (component count and per-node labels) and
`shortest_path` (all-pairs shortest-path matrix, with `method="D"`
Dijkstra and `unweighted=True`/`directed=False` options matching this
requirement's unweighted-undirected scope) — exactly the 2 primitives
REQ-AIDS-116's Statement names as its computational backend. Per-node
degree is a simple adjacency-matrix row sum needing no graph library at
all, and closeness centrality is directly computable from
`shortest_path`'s output with a documented, one-line formula
(`(reachable_count - 1) / sum(finite shortest paths from that node)`),
so no further graph-library primitive beyond `csgraph` is needed for
this requirement's scope (degree and closeness only — no betweenness or
eigenvector centrality in this increment).

## Decision / 決定
Implement `analyze_network` entirely on top of `scipy.sparse.csgraph`
(`connected_components` for `n_components`/`component_labels`,
`shortest_path(method="D", unweighted=True, directed=False)` for the
all-pairs distance matrix feeding the closeness-centrality formula) plus
a plain adjacency-matrix row sum for `degree`, introducing no new
third-party dependency. This matches REQ-AIDS-116's own Constraints,
which name `scipy.sparse.csgraph` explicitly and frame this as "this
change's dependency-minimization decision" in contrast to adding
`networkx`.

## Rejected alternatives / 却下した代替案
**Add `networkx` as a new `pyproject.toml` dependency and implement
`analyze_network` with its higher-level graph API**: rejected —
`networkx` is an unnecessary additional top-level dependency (slower
C-extension-free pure-Python algorithms for some operations, and a much
larger API than this requirement needs) for
functionality (`connected_components`, all-pairs shortest paths, simple
degree/closeness) that `scipy` — already a required dependency of this
project — provides directly via `scipy.sparse.csgraph`; introducing a
new dependency for capability an existing one already covers runs
against this project's established dependency-minimization practice
(the same reasoning REQ-AIDS-115 documents for introducing `sympy` only
because no existing dependency performs symbolic algebra — by contrast,
here an existing dependency already suffices, so no new one is
justified).
**Hand-roll connected-components/shortest-path/centrality algorithms in
pure Python instead of using either library**: rejected as unnecessary
reinvention — `scipy.sparse.csgraph`'s compiled implementations are
already available, tested, and in active use pattern elsewhere in the
scientific-Python ecosystem; reimplementing BFS/Floyd-Warshall-class
algorithms by hand would add maintenance burden and performance risk
with no corresponding benefit over the already-available library
primitive REQ-AIDS-116's Statement names directly.

## Consequences / 結果
`ai_data_scientist`'s dependency surface gains no new package for this
requirement; `analyze_network` is scoped to exactly what
`scipy.sparse.csgraph` and simple adjacency-matrix arithmetic can
express — unweighted, undirected, simple graphs with degree and
closeness centrality only. Should a future requirement need betweenness
centrality, eigenvector centrality, directed-graph support, or weighted
edges beyond what `scipy.sparse.csgraph` exposes, that would be a new,
separately-justified decision point (potentially revisiting the
`networkx` trade-off documented here), not an automatic extension of
this ADR.
