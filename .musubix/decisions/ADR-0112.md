# ADR-0112: scipy.signal-based peak/FWHM detection and a fixed-parameter AsLS baseline for the new signal_analysis module

## Context / 背景
GitHub #74 reports that `ai-data-scientist` has no first-class module for
spectral/scientific-signal analysis: users analyzing 2-column `x,
intensity` spectra (NMR, XRD, EELS, XPS, and similar) must bypass the
skill's own analysis-module surface, call `scipy.signal` directly from
standalone scripts, and hand-wire `sensitivity.SensitivityPlan` /
`run_sensitivity` around the result themselves to get a stability
classification — because no native module produces peak results in a
shape `sensitivity` can consume out of the box. A side effect noted in
the issue is that charts from such ad hoc scripts bypass
`visualization.build_image_output`/`record_chart`, so `notebook_audit`'s
visual-readability audit (#22) cannot evaluate them; fixing the
underlying analysis gap removes the pressure to reach for an ad hoc
script in the first place.

Two concrete technical decisions are needed to design DES-AIDS-094: (1)
which peak-detection/FWHM algorithm and library to use, and (2) which
baseline-correction algorithm(s) to implement for `method="linear"` and
`method="asls"`, including whether their internal tuning parameters
should be exposed in the public signature.

## Decision / 決定
Use `scipy.signal.find_peaks`/`scipy.signal.peak_widths` as the sole
peak-detection engine. `scipy` is already a direct dependency
(`scipy>=1.11` in `pyproject.toml`, already used elsewhere in this
package via `scipy.stats`, e.g. `stats_analysis.py`), so using its
`signal` and `sparse` submodules adds no new package dependency, only a
new import of already-installed functionality. `fwhm` is computed via
`peak_widths(..., rel_height=0.5)` and converted from sample units to
`x`-units by multiplying by the uniform sample spacing `dx = x[1] -
x[0]`. Optional pre-detection smoothing uses
`scipy.signal.savgol_filter` with a fixed `polyorder=3`, parameterized
only by the caller-supplied odd `window` length, which is validated
(`5 <= window <= len(y)`, odd) before use.

For `baseline_correct`, implement both methods the issue explicitly
requests:
- `method="linear"`: a two-point straight-line baseline through
  `(x[0], y[0])` and `(x[-1], y[-1])` — the simplest possible baseline
  model, adequate when the spectrum's true baseline is close to linear
  across the full scan range and the endpoints themselves sit on
  baseline (not on a peak).
- `method="asls"`: Asymmetric Least Squares smoothing (Eilers &
  Boelens, 2005), a standard, widely-used spectroscopy baseline
  technique that tracks a slowly varying baseline underneath sharper
  peaks without needing the user to hand-pick anchor points. Its three
  tuning parameters (`lam` smoothness, `p` asymmetry, `n_iter`
  iteration count) are fixed as internal constants (`lam=1e5`,
  `p=0.001`, `n_iter=10`) rather than exposed as additional public
  keyword arguments, so the public signature exactly matches what
  issue #74 requested
  (`baseline_correct(x, y, method="linear"|"asls")`) with no additional
  required decisions for a first-time caller, while still being
  deterministic and fully specified by REQ-AIDS-094 for testing.

## Rejected alternatives / 却下した代替案
**A custom from-scratch peak-finding algorithm (e.g. simple
derivative-sign-change detection)**: rejected because `scipy.signal`
already solves this robustly (noise-tolerant prominence-based
filtering, interpolated half-maximum width calculation) and is already
an installed dependency; reimplementing it would both duplicate
well-tested logic and very likely be less numerically robust than
`scipy`'s C-accelerated implementation, for no benefit — issue #74
itself names `scipy.signal.find_peaks`/`peak_widths` as the pattern
users were already hand-rolling.

**Exposing `lam`/`p`/`n_iter` as additional public keyword arguments
on `baseline_correct`**: considered, since it would let advanced users
tune AsLS for unusually broad or sharp baselines. Rejected for this
change because issue #74's requested signature is exactly
`baseline_correct(x, y, method="linear"|"asls")` with no additional
parameters, and exposing tuning knobs the issue did not ask for would
both widen the API surface prematurely and make REQ-AIDS-094's
acceptance criteria non-deterministic (different callers could get
different results from "the same" call). Fixed internal defaults can be
promoted to optional, additively-defaulted keyword arguments in a
future change if a concrete need arises, without breaking this
signature.

**Rolling-ball / morphological baseline estimation** (common in some
XRD/Raman tooling) instead of AsLS: rejected as a second baseline
method because the issue explicitly asks for `"linear"|"asls"` only;
AsLS is also simpler to implement deterministically with scipy's
sparse-matrix primitives (`scipy.sparse`, already available transitively
via `scipy`) than a morphological approach, and is the more common
default in general spectroscopy baseline-correction literature.

**A richer peak-result object (dataclass) instead of a plain dict**:
rejected because issue #74 explicitly asks for "a list of
`{position, fwhm, prominence, height}`" — a list of dicts is the most
direct implementation of the requested shape, and (unlike a dataclass)
requires no additional import for a caller who wants to pass the result
straight into `pandas.DataFrame(peaks)` or JSON-serialize it for a
notebook cell output, both common downstream steps for spectral-peak
tables.

## Consequences / 結果
- `signal_analysis.py` depends only on `scipy` (already a direct
  dependency) and `numpy` (already a transitive dependency via `scipy`/
  `pandas`); no new third-party dependency is introduced.
- `baseline_correct(..., method="asls")`'s fixed internal parameters mean
  it will not optimally handle every possible spectrum shape (e.g. an
  unusually sharp, very broad, or multi-scale baseline); if a future
  issue reports such a case, exposing the AsLS parameters as additional
  optional keyword arguments is the natural, additive next step and does
  not require a breaking signature change.
- `find_spectral_peaks` requires a strictly increasing, uniformly
  spaced `x`; a future change could relax this (e.g. via explicit
  resampling) if non-uniform spectral grids (common in some
  instrument exports) turn out to be a real recurring need, but that is
  out of scope for this change per CHANGE-029.
