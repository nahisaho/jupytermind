# ADR-0115: `convergence_guard.evaluate_convergence` treats a single textual `action_signature` as the sole repetition oracle, scoped to the last `min_consecutive` destination rounds

## Context / 背景
REQ-AIDS-098 was created after two real, sequentially-discovered bugs in
a hand-rolled Kaggle batch-analysis loop (`jupytermind-test/run_all.py`):
first, declaring `"converged"` from a single sub-threshold metric
transition, even while the metric was still clearly improving; second,
after requiring two consecutive sub-threshold transitions, discovering
that once the loop's finite catalog of distinct deep-dive actions was
exhausted, re-running the same deterministic action on the same data
produced an exact repeat (`relative_change == 0.0`), which trivially
satisfied the "two consecutive small transitions" rule through
tautological repetition rather than genuine evidence of a plateau. A
reusable library guard needs a way to distinguish "the metric stopped
moving because the model generalization stabilized" from "the metric
stopped moving because we literally repeated the same computation,"
without requiring the guard to inspect the caller's actual model
objects, training data, or hyperparameters.

## Decision / 決定
1. `action_signature` is a single opaque string, supplied by the caller
   per round, and is required (by REQ-AIDS-098's Statement) to fully
   encode the action's type, its effective parameters, and its input-data
   identity. `evaluate_convergence` treats textual equality of two
   `action_signature` values as sufficient proof that both rounds are a
   verbatim repeat of the same action on the same data — it never
   inspects any other field to corroborate or override this. This keeps
   the guard's contract small and pure (it never needs to know what a
   "GradientBoosting fit" or "feature-importance trim" actually is) while
   shifting the responsibility for constructing a sufficiently
   discriminating signature (e.g. including a hash of the effective
   hyperparameters and the training-data snapshot) onto the caller, where
   that domain knowledge actually lives.
2. Only the **candidate (later)** side of the duplicate check is scoped
   down to the trailing qualifying run's last `min_consecutive`
   destination rounds — never the full trailing run (which may be longer
   than `min_consecutive`) and never any non-contributing round further
   back in the same run. A candidate round is only ever one of those last
   `min_consecutive` destination rounds; a duplicate is never reported
   for, or because of, a non-contributing round acting as the candidate.
   The **earlier-match** side of the check is deliberately *not* scoped
   down the same way: for each candidate round, the search for a
   matching earlier round spans the full history up to that candidate,
   not just the contributing rounds or the trailing run — this is what
   lets the guard catch a repeat of a much earlier action (e.g. round 2
   verbatim-repeated at round 4), not only an immediately-preceding one.
   This mirrors exactly the minimal evidence actually required to declare
   "converged": only the last `min_consecutive` destination rounds are
   what the status is being staked on, so only *they* need to be checked
   for being free of repetition — but "free of repetition" must be
   verified against the caller's *entire* prior history, not an
   artificially narrowed window, or a genuine non-adjacent repeat would
   go undetected.
3. When more than one contributing destination round has a duplicate, or
   a single contributing round matches more than one earlier round, the
   verdict is resolved deterministically by a fixed two-level priority:
   greatest 1-based position among contributing (later) rounds first,
   then greatest 1-based position among that round's earlier matches.
   This guarantees `evaluate_convergence` is a pure function of its
   inputs (same arguments always produce the same verdict, including
   which single duplicate pair is reported) without requiring the guard
   to report every duplicate pair found, which would complicate the
   `ConvergenceVerdict` schema for comparatively little caller benefit —
   a caller mainly needs one concrete, reproducible example of the
   repetition to act on (e.g. log it, or feed it into a bug report),
   not an exhaustive enumeration.
4. Argument validation (`min_consecutive` must be a positive, non-`bool`
   `int`; `rel_tol` must be a finite number `>= 0.0`; every history entry
   must carry a finite numeric `metric` and a non-empty string
   `action_signature`) raises `ValueError` immediately, before any
   classification logic runs, rather than silently clamping or
   coercing invalid input. A convergence guard whose job is specifically
   to prevent a caller from fooling itself must not itself have a lenient
   failure mode that could mask a caller bug (e.g. accidentally passing
   `min_consecutive=0`, which would make every single transition
   trivially "qualify" regardless of the caller's intent).
5. `evaluate_convergence` is a pure function: it performs no file,
   notebook, or network I/O, never calls `ml_modeling.train_model` or any
   other analysis function, and never mutates its `history` argument.
   This keeps it trivially unit-testable and usable from both a batch
   script's plain Python loop and, later, directly from
   `insight_engine`/`lifecycle`-style call sites without any special
   session or notebook-handle plumbing.

## Rejected alternatives / 却下した代替案
**Structured, caller-supplied `action_type`/`params`/`data_hash` fields
instead of a single opaque `action_signature` string**: rejected because
it would force `evaluate_convergence` to define a canonicalization and
hashing policy for arbitrary caller parameter dictionaries (what counts
as "equal" parameters — exact float equality? Rounding? Nested
dict/array equality?), which is exactly the kind of domain-specific
judgment call this guard should not have to make. A single string gives
the caller full control over what "the same action" means for their own
domain, while keeping the guard's own comparison trivial (`==`) and
unambiguous.

**Treating any non-contributing destination round (outside the last
`min_consecutive` of the trailing run) as a candidate for duplicate
detection**: rejected because a longer qualifying run's earlier,
non-contributing rounds are not part of the evidence the
"converged"/"repetition_detected" verdict is actually based on; flagging
a duplicate *there* (as the candidate side of the check) would produce
false positives for histories that contain unrelated, earlier legitimate
repeats (e.g. a caller that intentionally re-ran an identical baseline
twice for calibration purposes long before the loop started
converging), which have no bearing on whether the *final* evidence for
convergence is trustworthy. This restriction applies only to which
rounds can be a *candidate*; the earlier-match search for a genuine
candidate is never restricted this way (see Decision 2).

**Reporting all duplicate pairs found, or requiring the caller to supply
a tie-breaking preference**: rejected in favor of one fixed, built-in
deterministic rule. A `list[tuple[int, int]]` or similar multi-pair
schema needlessly complicates `ConvergenceVerdict` for most callers, who
only need one concrete, reproducible example to act on; a configurable
tie-breaker adds an argument whose only purpose is resolving an edge
case most callers will never hit, at the cost of one more thing every
caller must understand.

**Silently clamping invalid `min_consecutive`/`rel_tol` to the nearest
valid value instead of raising**: rejected as inconsistent with this
module's purpose. A guard built specifically to stop a caller from
silently fooling itself about convergence must fail loudly, not
leniently, on malformed input to its own safety check.

## Consequences / 結果
Callers (starting with a future revision of `jupytermind-test/run_all.py`,
and any other iterative deep-dive loop built with this skill) gain a
single, independently-tested function that replaces hand-rolled
convergence/exhaustion logic, closing both bug classes found during this
change (weak single-point convergence, and repetition-masked false
convergence) by construction rather than by one-off vigilance. The
primary caller obligation this shifts onto them is constructing an
`action_signature` that is actually discriminating enough for their
domain (encoding effective parameters and input-data identity, not just
an action name) — an under-specified signature would silently defeat
the repetition check, but that failure mode is explicit and documented
rather than hidden inside the guard itself.
