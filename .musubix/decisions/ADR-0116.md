# ADR-0116: CSV ingestion uses a fixed `utf-8` → `cp1252` → `latin-1` encoding fallback chain, not charset auto-detection

## Context / 背景
GitHub #76 reports `ai_data_scientist.ingestion.ingest` raising an
unhandled `UnicodeDecodeError` for any CSV file not encoded as UTF-8,
discovered while batch-processing 100 real Kaggle datasets (6/100
failed). The existing `_sniff_csv_delimiter` helper already opens the
file once with `encoding="utf-8", errors="replace"` purely for delimiter
detection (a lossy, best-effort read that tolerates bad bytes), but the
actual `pd.read_csv` load call used no `encoding=` argument at all, so
pandas defaulted to strict UTF-8 and aborted ingestion entirely on any
non-UTF-8 byte sequence.

## Decision / 決定
1. `ingest()`'s CSV branch retries the load with a fixed, ordered
   fallback chain (two retries after the initial `utf-8` attempt:
   `cp1252` then `latin-1`) only after the `utf-8` attempt raises
   `UnicodeDecodeError`, rather than using a charset-detection library (e.g. `chardet`/`charset-normalizer`) to
   guess the encoding up front. `cp1252` is tried before `latin-1`
   because it is the de facto encoding of CSVs exported by Windows
   locale tools (Excel, legacy ETL pipelines) — the dominant real-world
   source of non-UTF-8 CSVs — and because `latin-1` (ISO-8859-1) never
   raises `UnicodeDecodeError` for any byte sequence, making it a safe,
   deterministic last resort that guarantees ingestion never aborts on
   encoding alone, at the cost of potentially misinterpreting the C1
   control-range bytes (`0x80`-`0x9F`) that `cp1252` and `latin-1`
   assign different meanings to — an unavoidable ambiguity without
   either embedded encoding metadata or a BOM, which this change does
   not attempt to solve in general.
2. No new third-party dependency is introduced. `cp1252` and `latin-1`
   are codecs already built into Python's standard library (`codecs`)
   and already accepted by `pandas.read_csv`'s `encoding=` argument, so
   this fix adds zero install-time or supply-chain surface area, unlike
   adopting a charset-detection library.
3. Only `UnicodeDecodeError` is intercepted and retried. Any other
   exception from `pd.read_csv` (e.g. `pandas.errors.ParserError` for a
   structurally malformed CSV, or `FileNotFoundError` for a missing
   file) propagates immediately and is never retried at a different
   encoding — retrying a non-encoding failure across three encodings
   would multiply unrelated failure latency for no benefit, since the
   same structural error would reproduce at every tier.

## Rejected alternatives / 却下した代替案
**Charset auto-detection via `chardet`/`charset-normalizer`**: rejected
for this fix. Both are heuristic, probabilistic classifiers that can
mis-detect short or mixed-content samples, adding a new dependency and a
non-deterministic failure mode (different detector versions/samples can
yield different guesses) in exchange for marginal improvement over a
fixed, well-understood two-tier fallback that already resolves the
reported real-world cases (Windows/Excel-exported CSVs). This remains a
candidate for a future change if a reported failure demonstrates the
fixed chain is actually insufficient in practice.

**`errors="replace"` (lossy decoding) instead of a second real encoding
attempt**: rejected as a silent data-corruption risk. `errors="replace"`
substitutes the Unicode replacement character (`\ufffd`) for every
undecodable byte, silently discarding information from the source data
(e.g. turning a legitimate accented character into an unrecoverable
placeholder) rather than attempting a real decoding that preserves the
original character when the file's true encoding is cp1252 or
latin-1 — exactly the common case this issue reports.

**Single fallback to `latin-1` only (skip `cp1252`)**: rejected because
`latin-1` and `cp1252` diverge specifically in the `0x80`-`0x9F` range,
which `cp1252` maps to common printable punctuation (smart quotes, the
Euro sign) that real-world Windows-exported CSVs frequently contain,
while `latin-1` maps those same bytes to rarely-used C1 control
characters. Trying `cp1252` first maximizes the chance of a correct,
human-meaningful decode for the dominant real-world case, falling back
to `latin-1` only when `cp1252` itself cannot decode a byte at all.

## Consequences / 結果
Any CSV byte-content, regardless of its single-byte encoding, is now
guaranteed not to fail due to `UnicodeDecodeError` alone; non-decoding
`pd.read_csv` failures (e.g. `pandas.errors.ParserError` for malformed
CSV structure) continue to propagate unchanged, directly resolving
GitHub #76's reported failures.
The caller is informed, via `IngestionResult.warnings`, whenever a
fallback encoding was used, preserving transparency about a
non-default code path being taken. The explicit non-goal — general
multi-byte-scheme (UTF-16/UTF-32) or BOM-based detection — is
documented so a future contributor does not mistake this fix for a
general-purpose encoding-detection feature; a CSV in such a scheme that
happens not to raise `UnicodeDecodeError` under an earlier tier while
still being mis-decoded is explicitly out of this ADR's scope.
