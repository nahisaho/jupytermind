# ADR-0082: Centralize external tool access behind a phase-attributed MCP gateway

## Context / 背景
`DES-AISCI-010` (`REQ-AISCI-015`, `CHANGE-001`) governs every external
domain-tool and literature-search call from ai-scientist phases. The
architectural trade-off is whether phases should talk to tool clients
directly for convenience, or whether ai-scientist should impose a single
gateway that always knows which phase initiated the call and can classify
failures consistently.

## Decision / 決定
`ai_scientist.mcp_gateway.McpGateway` is the sole MCP access surface for
ai-scientist-owned domain-tool and literature-search calls (`DES-AISCI-010`'s
scope). It is constructed with `clients: dict[str, McpClient]`, and phases
call `call_tool(server_name, tool_name, args, phase)` with an explicit
`phase` argument every time. The gateway first resolves the configured
client by server name, then delegates to `client.call_tool(...)`. Missing
clients and runtime exceptions from the client are both intercepted and
converted into a typed `MCPUnavailableError` via
`classify_mcp_failure(server_name, phase, exc)`.

This keeps phase handlers free of raw socket or HTTP ownership while making
server attribution and phase attribution part of the gateway contract, not a
best-effort logging side effect. Failure classification therefore happens at
the same structural boundary where outbound tool calls are routed.

One explicit, documented exception exists at the `data-analysis` phase
boundary: per `DES-AISCI-005`/ADR-0077, that phase calls
`ai_data_scientist.mcp_gateway.run_and_record(...)` directly, because it is
delegating to `ai-data-scientist`'s own already-governed MCP execution path
(REQ-AIDS-002/003/028/044) rather than performing ai-scientist-owned tool
access; `McpGateway` does not intermediate that sibling-feature call.

## Rejected alternatives / 却下した代替案
- **Letting each phase handler create and use its own HTTP/socket client**: rejected — that would violate the constraint that `DES-AISCI-010` is the sole tool-access path and would make it easy for one phase to bypass common failure handling or phase attribution.
- **Returning an error dictionary instead of raising `MCPUnavailableError`**: rejected — callers could accidentally treat the result as successful tool output and continue recording evidence, whereas a raised typed exception stops the phase cleanly.
- **Capturing the phase implicitly when constructing the gateway instead of requiring it on every call**: rejected — the same gateway instance can serve multiple phases, so phase must remain an explicit per-call input for accurate error attribution.

## Consequences / 結果
Future MCP-enabled phases must route through `McpGateway.call_tool(...)`
and supply their phase name explicitly; direct network access from phase
modules remains out of bounds. Covered by the acceptance tests in
`tests/test_ai_scientist_mcp.py`.
