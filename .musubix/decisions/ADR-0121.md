# ADR-0121: Detect Cox regression non-convergence by capturing `ConvergenceWarning` with an explicit `simplefilter("always", ...)` inside the capture scope, not by inspecting a fit-result attribute

## Context / 背景
REQ-AIDS-106 fits a single-covariate Cox proportional-hazards model via
`statsmodels.duration.hazard_regression.PHReg`. Unlike several other
statsmodels estimators, `PHReg`'s fit result exposes no boolean
`.converged` attribute and no `.mle_retvals` convergence dictionary, so
there is no result-object field this module can inspect after the fact
to detect optimizer non-convergence. Empirically, a complete-separation
dataset (verified: `durations=[1,2,3,4], events=[1,1,1,1],
covariate=[0,0,1,1]`) drives the fit toward an unbounded coefficient
(`coefficient≈-27.08`, `standard_error≈438233`) — both finite,
numerically "successful"-looking values that would pass a naive
`math.isfinite` check — while statsmodels emits a
`statsmodels.tools.sm_exceptions.ConvergenceWarning` through Python's
standard `warnings` mechanism. A plain `warnings.catch_warnings(record=
True)` block without an explicit filter reset can still silently miss
this warning if an earlier import or test run already installed a
`"once"` or `"ignore"` filter entry for the same warning category/message
in the process-wide filter list, since `catch_warnings()` alone saves
and restores filter state but does not itself force every warning to be
re-emitted.

## Decision / 決定
Call `.fit()` inside `warnings.catch_warnings(record=True) as caught:`
with `warnings.simplefilter("always",
statsmodels.tools.sm_exceptions.ConvergenceWarning)` set as the first
statement inside that same `with` block, then check `caught` for any
captured `ConvergenceWarning` after the call returns. This combination
guarantees the warning is re-emitted and captured on every call
regardless of any outer filter state. Treat 3 independent conditions as
non-convergence, any one of which triggers the `ValueError` naming
`durations`/`covariate` with constraint "fit did not converge": (1)
`PHReg().fit()` raising an exception; (2) a captured `ConvergenceWarning`;
(3) a non-finite `coefficient`, `standard_error`, or `p_value` in the
returned fit result (defense-in-depth for a hypothetical future
statsmodels version that stops emitting the warning for some currently
undiscovered separation pattern).

## Rejected alternatives / 却下した代替案
**Inspect only `math.isfinite` on the returned parameters, with no
warning capture**: rejected outright — the verified complete-separation
fixture produces fully finite-looking numbers (`coefficient≈-27.08`,
`standard_error≈438233`) that would pass this check despite being a
genuinely non-convergent, practically meaningless fit; this was the
original (insufficient) design before empirical verification caught the
gap.
**Use `warnings.catch_warnings(record=True)` with no `simplefilter`
call**: rejected — depends on ambient process-wide filter state set by
unrelated earlier code (e.g. a prior test or import already filtering
this exact warning class to `"once"`), which can silently suppress the
very re-emission this module depends on to detect non-convergence; this
was identified and fixed during this change's design review.
**Monkey-patch or subclass `PHReg` to expose an internal optimizer
convergence flag**: rejected as unnecessarily invasive and
version-fragile compared to the public, documented `warnings`-based
signal statsmodels already emits for exactly this situation.

## Consequences / 結果
`cox_ph_regression`'s non-convergence detection depends on
statsmodels continuing to emit `ConvergenceWarning` for unidentifiable
fits (current documented statsmodels behavior as of this change); should
a future statsmodels release change that behavior, the non-finite-value
fallback check (condition 3 above) remains as a secondary safety net,
though it alone is known to be insufficient for every realistic
separation pattern (per the verified fixture above) and must not be
relied on as the sole detection mechanism.
