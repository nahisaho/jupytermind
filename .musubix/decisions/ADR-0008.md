# ADR-0008: Native .venv-managed background daemon for the Jupyter MCP runtime (not Docker)

## Context / 背景
REQ-AIDS-034 through REQ-AIDS-037 require jupytermind to automatically
install and start JupyterLab and the Jupyter MCP server so the execution
gateway (DES-AIDS-004) has a real backend to call, instead of requiring the
user to hand-supply an `MCPClient`. Two process-management strategies were
considered: containerizing JupyterLab/jupyter-mcp-server/ipykernel with
Docker, or managing them as native background processes inside the same
`.venv` already bootstrapped by `bin/ai-data-scientist.js doctor`.

## Decision / 決定
Manage JupyterLab and jupyter-mcp-server as native background processes
inside the project's existing `.venv`, started on demand on first execution
request (REQ-AIDS-034), bound to `127.0.0.1` with an auto-selected port and a
randomly generated token, and tracked via a machine-local state file
(PID, port, token) so later, independent CLI invocations detect and reuse
the same still-running daemon (REQ-AIDS-035) rather than starting a
duplicate one. Explicit `status`/`stop` commands (REQ-AIDS-037) give the
user direct control over the daemon's lifecycle.

## Rejected alternatives / 却下した代替案
- Docker-based packaging (`docker pull datalayer/jupyter-mcp-server` plus a
  JupyterLab image): rejected because it would add a hard Docker
  daemon/Desktop dependency, directly contradicting the project's core
  "install via `npm install` only" promise; it also complicates notebook
  file persistence (bind mounts) for no isolation benefit that matters here,
  since the same `.venv` already isolates the Python dependency graph.
- Ephemeral per-CLI-invocation process lifetime (start and stop within a
  single command run): rejected because JupyterLab/jupyter-mcp-server
  startup is too slow to repeat on every single analysis instruction; reuse
  across invocations (background daemon) is required for interactive
  responsiveness.
- Fixed, user-configured port/token: kept as a non-default option in
  REQ-AIDS-034's acceptance wording space, but the default is
  auto-random-everything to avoid silent collisions between multiple
  concurrent jupytermind projects on one machine.

## Consequences / 結果
jupytermind takes on a new runtime responsibility (process lifecycle,
PID/state-file bookkeeping, orphan cleanup) that did not exist before;
DES-AIDS-012 owns this responsibility exclusively so the rest of the system
keeps depending only on the existing `MCPClient` contract from DES-AIDS-004.
Because the daemon persists across invocations, a machine restart or crash
can leave a stale state file pointing at a dead PID; DES-AIDS-012's health
check before reuse must treat a dead-PID state file as "no runtime running"
rather than trusting the file blindly.
