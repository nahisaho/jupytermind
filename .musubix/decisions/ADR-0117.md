# ADR-0117: Reject a non-convergent or physically nonsensical nonlinear curve-fit result by raising `ValueError` from inside `run_*`, not by returning a partial or NaN-valued fit

## Context / 背景
REQ-ACHEM-120 (four-parameter logistic dose-response fitting) and
REQ-ACHEM-140 (Michaelis-Menten enzyme-kinetics fitting) both fit a
nonlinear model to a small user-supplied dataset via
`scipy.optimize.curve_fit`. Pre-fit input defects (too few points, a
non-finite or non-positive value, mismatched lengths, or fewer than 2
distinct values in either array) are already rejected by
DES-ACHEM-002's atomic `validate_parameters` before `run_*` is ever
called, using the uniform `{ok: false, parameter, constraint}` shape
every other atomic module uses. But `curve_fit` can still fail in two
distinct ways *after* that pre-fit validation has already passed: (1) it
can raise `RuntimeError` when the optimizer cannot converge within its
iteration budget; or (2) it can return a numerically "successful" result
that is nonetheless physically meaningless (a non-finite fitted
parameter, or a finite `ic50 <= 0` / `vmax <= 0` / `km <= 0`) when the
supplied data does not actually constrain the model. Both REQ-ACHEM-120
and REQ-ACHEM-140's own Acceptance criteria already specify, in exact
words, that both of these post-fit failure modes are "rejected with
`ValueError`" — a literal raised Python exception, not the
`{ok: false}` dict shape DES-ACHEM-002 returns for pre-fit validation —
so this ADR documents and names that already-specified post-fit
detection mechanism precisely, rather than inventing a new one.

## Decision / 決定
Inside each of `run_dose_response_fit` (REQ-ACHEM-120) and
`run_enzyme_kinetics` (REQ-ACHEM-140), wrap the `curve_fit` call and
check its result for exactly these 2 post-fit conditions, raising
`ValueError` (not returning a dict) on either:
1. `curve_fit` raises `RuntimeError` (optimizer failed to converge) —
   caught and re-raised as `ValueError`, naming `concentrations`/
   `responses` (REQ-ACHEM-120) or `substrate_concentrations`/
   `velocities` (REQ-ACHEM-140) with the exact constraint string "fit
   did not converge", matching each requirement's Acceptance verbatim.
2. A fit that does converge but yields a non-finite fitted parameter, or
   a finite `ic50 <= 0` (REQ-ACHEM-120) / `vmax <= 0` or `km <= 0`
   (REQ-ACHEM-140) — raised identically as `ValueError` naming the same
   parameters, with the exact constraint string "fitted parameters must
   be finite with ic50 > 0" (REQ-ACHEM-120) or "fitted parameters must
   be finite with vmax > 0 and km > 0" (REQ-ACHEM-140).
Both modules share this same 2-condition post-fit policy and the same
raised-`ValueError` mechanism (rather than DES-ACHEM-002's dict shape),
since both requirements specify it identically; a module's own handler
wrapper (DES-ACHEM-001) is responsible for catching this `ValueError`
and converting it into the dispatch layer's own `ModuleOutcome`
rejection shape, exactly as it would for any other uncaught exception
a `run_*` function raises.

## Rejected alternatives / 却下した代替案
**Return the raw `curve_fit` result unconditionally, including
`RuntimeError`-triggering or sign-inverted fits**: rejected — this
would silently surface nonsensical `ic50 <= 0`/`vmax <= 0`/`km <= 0`
values as if they were valid kinetic parameters, contradicting both
requirements' explicit Acceptance criteria.
**Report the post-fit failure via DES-ACHEM-002's `{ok: false,
parameter, constraint}` dict shape, matching every other atomic
module's pre-fit validation convention**: rejected — both
REQ-ACHEM-120's and REQ-ACHEM-140's own Acceptance text explicitly says
"rejected with `ValueError`" for this specific post-fit case, a
deliberate deviation already approved at the requirements stage for
this one post-fit check (pre-fit validation still uses the standard
dict shape via DES-ACHEM-002, unchanged); reusing the dict shape here
would contradict the already-approved requirements text.
**Silently clip a negative `ic50`/`vmax`/`km` to zero or its absolute
value**: rejected — this would fabricate a plausible-looking but
unsupported number rather than honestly reporting that the supplied
data does not constrain a physically valid fit.

## Consequences / 結果
Both REQ-ACHEM-120 and REQ-ACHEM-140 share one documented post-fit
rejection policy and one raised-`ValueError` failure mechanism distinct
from DES-ACHEM-002's pre-fit dict shape, keeping their design blocks
(DES-ACHEM-120, DES-ACHEM-140) and acceptance-fixture structure
consistent with their own approved requirements text. Each module's
handler wrapper (DES-ACHEM-001) must catch this `ValueError` explicitly
and translate it into the standard dispatch-level rejection outcome,
so a caller of `dispatch(...)` never sees a raw uncaught exception
regardless of which of the 2 layers (pre-fit dict-shape validation, or
post-fit raised `ValueError`) produced the rejection. A future nonlinear
curve-fitting module added to `ai-chemistry-scientist` should reuse this
same 2-condition policy rather than inventing a new one, documenting any
deviation in its own requirement text first.
