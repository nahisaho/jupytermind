# ADR-0095: Dispatch `box`/`heatmap` as dedicated plotting branches ahead of the shared pandas/matplotlib path (DES-AIDS-073)

## Context / 背景
`DES-AIDS-073` (REQ-AIDS-085) requires `render_chart` to add `box`, `barh`,
and `heatmap` kinds while preserving the current `scatter`/`line`/`bar`/
`hist` code path byte-for-byte when no new parameters are used. `barh`
needs no new plotting logic beyond selecting the horizontal orientation
pandas already supports, but `box` (grouping numeric values per distinct
`x` category, or an all-numeric fallback) and `heatmap` (correlation matrix
vs. an already-square labeled matrix, plus tick labels and a colorbar) have
no equivalent in the existing `_plot_with_existing_paths`/`_plot_with_hue`
dispatch, and neither kind participates in hue-based legend grouping or
error-bar plotting.

## Decision / 決定
Add two dedicated module-private functions, `_plot_box_chart` and
`_plot_heatmap`, and dispatch to them in `render_chart` *before* the
existing `hue is not None` / `_plot_with_existing_paths` branching
(`kind == "box"` / `kind == "heatmap"` checked first, unconditionally).
`_plot_box_chart` derives one box per distinct `x` value via
`df.groupby(x, sort=False, dropna=False)` when both `x` and `y` are given,
falls back to a single-series boxplot of `y` when only `y` is given, and
falls back further to one box per numeric column when neither is given.
`_plot_heatmap` uses the named-column correlation matrix when both `x` and
`y` are supplied, otherwise detects a pre-built square matrix (numeric
dataframe whose index labels equal its column labels) and renders it
directly, falling back to the all-numeric-columns correlation matrix
otherwise; it always renders via `Axes.imshow` with explicit tick labels
and a `fig.colorbar` call. `barh` requires no new function: it is handled
by passing `kind="barh"` straight through to the existing pandas-backed
bar paths in `_plot_with_existing_paths`/`_plot_with_hue`, which already
accept a `kind` string.

## Rejected alternatives / 却下した代替案
- Routing `box`/`heatmap` through the existing `hue`/error-bar dispatch
  functions by adding `if kind in ("box", "heatmap")` branches inside them:
  rejected because neither kind has a meaningful hue-driven legend or
  error-bar semantics (`DES-AIDS-074`/`DES-AIDS-075` explicitly exclude
  `heatmap` from legend/error-bar logic), so interleaving their dispatch
  logic into the hue/error helpers would force those helpers to special-case
  two kinds they structurally do not apply to, rather than keeping the
  dispatch boundary aligned with where the behavior actually differs.
- A generic `kind -> callable` dispatch table replacing the existing
  `if`/`elif` chain in `render_chart`: rejected as a larger refactor of the
  pre-existing `scatter`/`line`/`bar`/`hist` dispatch than this change's
  scope requires, and because the existing chain's ordering (dedicated
  kinds checked first, then hue, then the shared existing-paths fallback)
  already expresses the needed precedence without introducing an
  indirection layer.

## Consequences / 結果
`box` and `heatmap` are structurally exempt from hue-driven legend
grouping and `xerr`/`yerr` error-range plotting (`DES-AIDS-074`/
`DES-AIDS-075` depend on `DES-AIDS-073` but do not extend these two kinds);
any future requirement to add grouping or error ranges to `box`/`heatmap`
needs a new design decision rather than falling out of the existing hue/
error-bar helpers. Adding a further new `kind` that needs genuinely new
plotting logic should follow this same pattern: a dedicated
`_plot_<kind>_chart` function checked before the hue/existing-paths
branches, documented with its own design section.
