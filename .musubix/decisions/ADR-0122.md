# ADR-0122: Validate `symbolic_math.symbolic_compute` input with a mandatory AST whitelist walk before any `sympy` parsing, not with `sympy`'s own `__builtins__={}` sandbox alone

## Context / 背景
REQ-AIDS-115 introduces `ai_data_scientist.symbolic_math.symbolic_compute`,
which evaluates a caller-supplied algebraic `expression` string with
`sympy` (`solve`/`diff`/`integrate`/`simplify`). `sympy.sympify` and
`sympy.parsing.sympy_parser.parse_expr` can be configured to evaluate
inside a restricted namespace (e.g. `sympify(expr, locals={},
evaluate=True)` with `__builtins__` suppressed), which looks at first
glance like a sufficient sandbox for untrusted string input. During this
change's rubber-duck design review, that assumption was tested
empirically against the classic Python sandbox-escape chain
`().__class__.__base__.__subclasses__()` (and the related
`__import__('os').system(...)` chain): both are confirmed exploitable
against a bare `__builtins__`-suppressed `sympify`/`eval`-style sandbox,
because suppressing the `__builtins__` name does not remove attribute
access (`__class__`, `__base__`, `__subclasses__`) or the ability to
call whatever object that attribute chain resolves to — an attacker can
reach the full live object graph (including `subprocess`-capable
classes reachable from `object.__subclasses__()`) without ever naming a
builtin directly. `sympy`'s own parser additionally accepts a much
richer expression grammar (implicit multiplication, function calls,
power towers) than this requirement needs, widening the attack surface
further if that parser is the first thing to see untrusted text.

## Decision / 決定
Before any `sympy` object is constructed, parse `expression` with
Python's own `ast.parse(expression, mode="eval")` and walk every node in
the resulting tree, rejecting the whole request (`ValueError` naming
`expression`) unless every node's type is in the fixed whitelist
`{Expression, BinOp, UnaryOp, Call, Name, Load, Constant, Add, Sub,
Mult, Div, Pow, Mod, FloorDiv, USub, UAdd}`, every `Constant` value is
an `int`/`float`, every `Call.func` is a bare `Name` in the fixed
elementary-function allowlist `{"sin","cos","tan","asin","acos","atan",
"sinh","cosh","tanh","exp","log","sqrt","Abs"}`, and no `Call` carries
keyword arguments. Only a string that passes this whitelist walk in its
entirety is ever handed to `sympy.sympify`/`parse_expr`. This whitelist
has no `Attribute`, `Subscript`, `Tuple`/`List`/`Dict`/`Set`, `Lambda`,
comprehension, `Compare`, `BoolOp`, or `Import` node, so no attribute
traversal (including the verified `().__class__...` chain), subscript,
import, or call to anything outside the 13 named elementary functions
can ever reach `sympy`'s parser or any Python evaluation step — the
rejection happens at the pure-syntax-tree stage, before any object
graph is constructed or traversed.

## Rejected alternatives / 却下した代替案
**Rely on `sympy.sympify`/`parse_expr` with `__builtins__={}` or an
empty `locals=`/`global_dict=` as the sole safeguard**: rejected —
confirmed exploitable in this change's own rubber-duck review via
`().__class__.__base__.__subclasses__()` and `__import__(...)` chains;
suppressing `__builtins__` does not prevent attribute-based traversal
of the live Python object graph, so this alone is an insufficient
sandbox for untrusted expression text.
**Use a regex/string-blocklist filter (e.g. reject strings containing
`__`, `import`, `exec`) instead of an AST whitelist**: rejected as
fundamentally unsound — blocklists are trivially bypassed by
alternative spellings, whitespace tricks, or any construct the author
did not anticipate, whereas a positive AST whitelist only ever accepts
the fixed, enumerated grammar this requirement actually needs.
**Run the untrusted `sympy` evaluation in a subprocess or restricted
interpreter (e.g. `RestrictedPython`) instead of static AST
validation**: rejected as disproportionate operational complexity
(process-per-call overhead, new dependency, new failure modes) for a
single-variable elementary-algebra evaluator whose entire needed
grammar is small enough to enumerate and check statically in-process.

## Consequences / 結果
`symbolic_compute` never calls `sympy.sympify`/`parse_expr` on text that
has not already passed the AST whitelist walk, so the module's security
boundary is Python's own `ast` module plus this fixed node/name
whitelist, not `sympy`'s parser or evaluation internals. Any future
expansion of the supported grammar (e.g. a new elementary function)
requires an explicit whitelist addition and re-review, which is the
intended friction; this also means legitimate expressions using
constructs outside the whitelist (e.g. complex numbers, symbolic
constants like `pi`, multi-variable systems) are out of scope for this
increment per REQ-AIDS-115's own Constraints, not silently permitted.
