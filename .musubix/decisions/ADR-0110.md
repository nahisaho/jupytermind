# ADR-0110: Split CHANGE-025 remediation into in-session gate repair and post-session workflow reconciliation

## Context / 背景
CHANGE-025 exists because `npx musubix3 approval record release` runs the full,
unscoped repository gate and is blocked by pre-existing baseline debt on clean
`main`: `workflow`, `tdd`, `change-history`, `change-completeness`,
`performance`, and, in this worktree until tooling is restored, `commands`.

The key complication is musubix3 GitHub issue #63, documented in the
repository's `sdd-change` skill: while the current Copilot session is still
running, its live transcript cannot be sanitized into a form that clears
`WORKFLOW_INVOCATION_UNVERIFIED`. Therefore `workflow` cannot truthfully pass
inside the same live session that is producing CHANGE-025.

At the same time, the other baseline failures (`tdd`, `change-history`,
`change-completeness`, `performance`, `commands`) are ordinary repository
evidence/tooling debt and are remediable within the active session.

## Decision / 決定
Model CHANGE-025 as a two-stage governance remediation:

1. **In-session remediation:** repair every required non-approval gate check
   that is honestly fixable while the transcript is still live:
   `tdd`, `change-history`, `change-completeness`, `performance`, and
   `commands`.
2. **Post-session workflow reconciliation:** after this Copilot session has
   ended, run the documented follow-up workflow procedure against the closed
   transcript: `workflow-sanitize`, `workflow-verify`, and
   `workflow waiver record-all`, then rerun the full `gate --json`. Even once
   this reconciliation makes `workflow` pass, `approval record release` for
   CHANGE-025 still cannot succeed while decision 4's `CHANGE-003` blocker
   remains unfixed upstream; record release approval only once that blocker
   is independently resolved and a subsequent full gate run passes.
3. **Waiver record/refresh for CHANGE-001/CHANGE-019:** for `CHANGE-001`'s
   nine `{CHANGE_RED_UNPROVEN,CHANGE_GREEN_UNPROVEN,CHANGE_COMPLETENESS_TDD}` x
   `REQ-AISCI-004/017/024` scopes (each already waived once, now stale) and
   the equivalent nine never-waived `CHANGE-019` scopes for the same 3
   requirements, record or refresh a change waiver (DES-RELGATE-002) rather
   than attempting to reproduce a historical Red/Green test run — the
   diagnostics are genuinely still firing today, which is exactly the
   condition `change waiver record` is designed for, and no CLI operation can
   retroactively reproduce an already-recorded, immutable historical phase's
   test execution anyway.
4. **Out-of-scope disclosure for CHANGE-003, deferral of CHANGE-020:**
   `CHANGE-025`'s requirement set was locked at its `requirements`
   phase-record to REQ-RELGATE-001 through -005 (musubix3's `change.js`
   rejects re-recording an already-recorded singular phase, so no requirement
   can be added to this change after the fact). Therefore CHANGE-003's
   `CHANGE_PHASE_ORDER:quality is not after green` diagnostic is disclosed, in
   REQ-RELGATE-001's acceptance criteria, as a permanent, CLI-unfixable
   limitation and accepted residual risk outside CHANGE-025's own remediable
   scope — tracked upstream at `nahisaho/musubix3#56` (reopened: the shipped
   `CHANGE_ORDER_MIGRATION_REQUIRED` fix only covers missing/non-integer order
   metadata, not this "later TDD redo outranks an already-recorded singular
   phase" case) — rather than attempted here. Because this diagnostic is
   error-severity and `approval record release` hard-fails on any
   non-passing required check across the full repository with no suppression
   mechanism, it also blocks release approval for CHANGE-025 itself and every
   other change until musubix3 ships a fix. CHANGE-020's genuinely missing
   `REQ-AISCI-023` TDD cycle is a separate, independently achievable defect
   unrelated to CHANGE-025's locked requirement set; it is deferred to a
   future successor change rather than folded into this one.

This ADR intentionally keeps the gate rules unchanged. It changes the
*remediation order and handoff model*, not the repository's quality bar.

## Rejected alternatives / 却下した代替案
Attempting to clear `WORKFLOW_INVOCATION_UNVERIFIED` inside the live session:
rejected because the CLI itself structurally refuses the needed transcript form
until the session terminates, so any in-session "clearance" would be false.

Weakening REQ-RELGATE-001 so workflow never has to pass:
rejected because the real release path (`approval record release`) still
requires `workflow` to pass eventually; permanently excluding it would not solve
the actual repository blocker.

Hand-editing evidence files (`workflow`, `performance`, or TDD ledgers):
rejected because CHANGE-025 is specifically about restoring truthful gate
evidence; direct ledger editing would bypass the repository's evidence model and
create stronger claims than the tools can verify.

Reconstructing a fresh Red/Green cycle for CHANGE-001/CHANGE-019's already-
passing implementations by temporarily reverting code in a worktree:
rejected after confirming `hasValidTddCycle`'s order-window check (`change-
evidence.js`) requires the TDD cycle's `red`/`green` order to fall at or before
the already-recorded, fixed `batch.red.order` — a freshly run `tdd red`/`tdd
green` today always receives a strictly later order, so it can never satisfy
the window regardless of how faithfully the revert is performed; the only
truthful remediation for these scopes is waiver record/refresh (decision 3).

Folding CHANGE-020's fresh TDD cycle and CHANGE-003's disclosure into a new
REQ-RELGATE-006 within this same change: rejected after confirming
`change-record`'s `requirements` phase for CHANGE-025 was already recorded
with exactly REQ-RELGATE-001 through -005, and the CLI provides no supported
operation to amend an already-recorded change's declared requirement set;
doing so anyway would desynchronize the CHANGE document, requirements.md, and
the recorded evidence, and would itself trip `CHANGE_REQUIREMENTS_MISMATCH`.

Inventing a `change-record` "reorder" or "supersede" operation for CHANGE-003:
rejected because no such operation exists in the installed musubix3 CLI, and
adding one would require an upstream musubix3 change outside this repository's
control; disclosed as residual risk instead (decision 4).

## Consequences / 結果
CHANGE-025's design and CHANGE document must explicitly distinguish:

- what this live session is expected to make pass now;
- what is blocked until a later session with a closed transcript;
- why CHANGE-025's own release approval cannot be recorded even after that
  post-session workflow pass, because of decision 4's independent,
  upstream-blocked `CHANGE-003:CHANGE_PHASE_ORDER` diagnostic
  (`nahisaho/musubix3#56`).

This keeps the remediation honest and operationally useful: unrelated future
changes have their stale-waiver, stale-TDD-evidence, missing-performance-
provenance, and missing-command-execution debt repaired, while the remaining
`workflow` step has a precise, reproducible handoff, and the one genuinely
unfixable `CHANGE-003` blocker is disclosed and tracked rather than hidden —
no change in this repository, including CHANGE-025, can obtain release
approval until that upstream defect is fixed.
