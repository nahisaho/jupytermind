# ADR-0084: Manage on-demand MCP runtimes in a session-scoped registry keyed by server name

## Context / 背景
`DES-AISCI-012` (`REQ-AISCI-017`, `CHANGE-001`) needs to start configured
managed MCP servers lazily, reuse them during the session, and prove that a
runtime is genuinely healthy before phases depend on it. The architectural
choice is how to represent and cache those runtimes without starting extra
processes or confusing one server instance with another.

## Decision / 決定
`ensure_managed_server(entry, timeout_ms=30000, phase="managed-startup")`
uses a module-scoped `_RUNTIMES` registry keyed by configured server name.
For a missing or unhealthy entry, it allocates a free `127.0.0.1` port,
substitutes that port into both `entry.launch_command` and
`entry.endpoint_template`, launches the process with `subprocess.Popen`, and
polls `endpoint + health_check_path` until it returns HTTP 200 or the
deadline expires. On success it stores `(process, RuntimeInfo, health_path)`
in the registry and returns `RuntimeInfo{pid, port, endpoint}`; on timeout
or crash it stops the process and raises a classified unavailability error.

`status(server_name)` revalidates liveness and health before reporting a
cached runtime, and `stop(server_name)` terminates only the process
currently registered for that name. This yields lazy startup, per-name
reuse keyed on configured server name, and health-checked availability for
the remainder of the session.

**Resolved** (originally a known limitation, closed by CHANGE-019 per
jupytermind#66): `ensure_managed_server(...)` now takes a per-server-name
`threading.Lock` (via `_lock_for`, mirroring `project_manager`'s per-path
lock pattern) around its entire check-then-start critical section, so two
concurrent first-use calls for the same name can no longer both start a
process; `status`/`stop` use the same per-name lock for consistency. A new
`_require_loopback_endpoint(...)` check, run before any port allocation,
rejects any configured `endpoint_template` host that is not a literal
loopback address or a name resolving exclusively to loopback addresses
(via `_is_loopback_host`, not a fixed allowlist, so a hosts-file/DNS
override cannot bypass it; see `TEST-AISCI-046`). The small residual
TOCTOU window against an
*external, non-ai_scientist* process stealing the allocated port between
`_allocate_port()` and `Popen` is accepted as an explicit, documented
residual risk (full elimination would need socket-fd-passing into the
spawned process, which is out of scope for jupytermind#66's own proposed
fix). Covered by `TEST-AISCI-042` and `TEST-AISCI-043`.

## Rejected alternatives / 却下した代替案
- **Starting every managed MCP server eagerly during ai-scientist startup**: rejected — many sessions will never use every configured server, so eager startup would waste processes, ports, and failure surface for no user benefit.
- **Keying the runtime cache by chosen endpoint or PID instead of configured server name**: rejected — callers request servers by configured name, and different restarts of the same named server must still be treated as one logical runtime slot.
- **Considering a process ready as soon as `Popen(...)` succeeds, without waiting for HTTP 200 on the health endpoint**: rejected — successful spawn does not prove the server is listening or serving tools yet, so reuse would become racy and violate the documented readiness contract.

## Consequences / 結果
Future managed-server enhancements must preserve per-name reuse and the
rule that health checks, not process spawn alone, establish readiness.
Loopback-only binding and registry-level concurrency safety are now
enforced (see Resolved above); the external-process port-steal window
remains an accepted residual risk, not yet closed. Covered by the
acceptance tests in `tests/test_ai_scientist_mcp.py`.
