# ADR-0015: Static manifest dispatcher instead of dynamic plugin discovery for simulation modules

## Context / 背景
REQ-AIMS-001/002 require `ai-materials-scientist` to route a bilingual
natural-language request to exactly one of seven simulation modules
(phase-field, molecular dynamics, classical Monte Carlo, kinetic Monte
Carlo, crystal plasticity, finite element, CALPHAD), asking a
clarification question on an ambiguous match and rejecting on no match.
DES-AIMS-001 needs a concrete dispatch mechanism.

## Decision / 決定
Reuse the manifest-dispatch pattern already proven in `ai-scientist`
(`src/ai_scientist/manifest.py`): a single static Python dict literal maps
each method name and its bilingual synonyms to exactly one module handler
function. `dispatch()` classifies the request text against this static
manifest and invokes at most one handler. The manifest is checked into the
skill package; it is not discovered at runtime from installed plugins or
external files.

## Rejected alternatives / 却下した代替案
- Dynamic plugin discovery (e.g., entry-point/setuptools plugin scanning):
  rejected because it adds a runtime dependency surface and
  nondeterminism (discovery order, third-party plugin injection) with no
  concrete requirement calling for runtime-extensible modules; the seven
  modules are fixed by REQ-AIMS-010 through 070.
- A single large `if/elif` chain instead of a manifest dict: rejected
  because it does not give a single inspectable source of truth for
  REQ-AIMS-002's bilingual synonym matching and is harder to keep in sync
  with the seven-module acceptance table.

## Consequences / 結果
Adding an eighth simulation module later requires updating the static
manifest and its synonym list, not just dropping in a new file; this is an
accepted cost in exchange for deterministic, fully auditable dispatch
behavior.
