# ADR-0127: 歴史的根拠の再現と追記型記録の保持

Status: proposed
Date: 2026-10-29

## Context

現在の機能テストは成功するが、過去のテスト変更と欠落した TDD により
全体の必須ゲートが通らない。実際のテスト変更は `tdd migrate` で補えない。
一方、未注釈 helper を含む宣言範囲による失効もあり、区別が必要。

## Decision

変更されていない関数は、assert を落とさず宣言境界を整理する。
保存済みの有効な fingerprint と現在の CLI の計算結果を照合する。
新たな根拠が必要な場合は実在する過去の Git 入力と現在版を隔離環境で比較し、
同じテスト・コマンドによる現在の Red / Green として記録する。
当時の開発順序を復元したとは主張しない。
保存されていない実行についても、当時あったとは主張しない。

TEST-AISCI-024 の静的チェックは要求書とテスト注釈だけを読むため、
許可対象の実装を差し替えても Red を再現できない。
この最新サイクル `1a91db34-ed68-4b5a-b225-a7cbe99cd316` だけを、
要求・設計とは別の人間の個別承認後に正規 CLI で archive する。
同じ要求を直接検証する TEST-AISCI-035 の既存サイクル
`0d264714-5c38-498a-9dbc-2b4f4f358849` を維持する。
その有効な Red / Green と現在の宣言 fingerprint を確認し、両テストを実行する。
元の全記録を保持し、退役を新しい検証の成功とは呼ばない。
詳細な前提と差分の確認は DES-GATE-RECOVERY-001 の実行契約に従う。
この例外を他のサイクルや失敗テストに広げない。
この TEST-AISCI-024 の退役は個別承認後に実施済みであり、
上記の実施条件と全記録を保持し、再実施しない。

TEST-AIDS-340 は祖先に対象がない場合の既存フォールバックを検証する。
実在する修正前の Git 版でも成功し、失敗を再現できなかった。
対象の未完了 cycle `d338d2a4-d6db-45e0-b711-2266228eb5bb` だけに、
別の限定例外を設ける。要求・設計承認とは別に個別承認を得た後、
正規 CLI で archive する。
同じ REQ-AIDS-093 の祖先探索を直接検証する TEST-AIDS-331 の
有効な cycle `33a2818f-da5d-4bbb-b714-08f6bc146cf8` と現在の宣言を照合する。
両テストを現在版で実行し、元の全記録を保持する。
退役を新しい Red / Green や失敗再現の成功と呼ばない。
詳細な前提と実行直前の記録に対する差分確認は設計の実行契約に従う。
この別の例外も他のサイクルや失敗テストに広げない。

停止した隔離コピーの 14 組の成功と無効な TEST-AIDS-340 の試行は監査用に残す。
これらを取り込まず、改訂承認と個別操作後の新しい固定点から
別の隔離コピーで残る 17 要求・30 テストを最初から再現する。
古い記録を merge したり手動で rebase したりして、入力の一致確認を回避しない。

作業元は固定し、CLI が生成したファイルの byte 列だけを排他的に移送する。
元の全記録が保持されること、作業元に競合更新がないことを確認する。
複数ファイルの部分更新は成功ではなく、保存済み hash で判定する復旧対象とする。
履歴 waiver は現在の許可対象診断に限定し、別途人間の承認を受ける。
候補抽出と準備状況の判定は副作用のない Python 関数に分離する。
移送が未完了なら、gate が成功しても準備完了とは報告しない。

正規 writer lock は公開 Node API のため、専用の小さな
`scripts/gate_recovery_transport.mjs` が保持する。
Python 側は終了コードと完了 manifest を確認する。
この境界は artifact 移送に限定し、独自のテスト実行器や SDD CLI を作らない。
実装が過去に存在しないテストでは import を関数内へ移し、
assert を変えずに対象テスト内の失敗を観測する。

## Rejected alternatives

- 失敗を作るためだけの改変、偽のレポート、hash chain の手編集。
- 全 601 サイクルの削除と、過去の根拠がない状態からの一括作り直し。
- TDD や必須チェックの無効化、閾値の引き下げ。
- 現在の構造的前提を満たさない native evidence merge の強制利用。
- 証拠を共有したまま複数 writer を動かす操作。
- 静的チェックの Red を作るためだけの要求書・テストの改変。
- 別の有効な直接検証と個別承認がない archive。

## Consequences

過去版で契約の失敗を確認できない場合、復旧を完了とは報告できない。
ただし TEST-AISCI-024 と TEST-AIDS-340 の指定した各 1 サイクルだけは、
それぞれ上記の限定例外の全条件を満たす場合に退役できる。
段階とレポートの出所を保存するため、単なるテスト再実行より手順が増える。
現在の機能契約と検証の厳しさは保たれる。
非承認チェックの成功後にも、artifact に結び付いた release 承認が必要。

ai-scientist の npm 同梱指定の欠落 / 追加を確認した。

TEST-AIDS-215 は初期 commit の実在する explainability 実装で、
3 特徴すべての多クラス重要度が参照値と異なる assertion failure を観測した。
同じテストとコマンドを現在の実装に戻すと成功した。
これは独立した pytest の事前確認であり、保護された TDD 記録ではない。
REQ-AIDS-021 の ranking と REQ-AIDS-082 のラベルを区別して対応付ける。

最初の隔離 fixture は承認の不一致で Red を拒否した。

公開 writer lock 内で CLI が生成した 3 ledger を別の使い捨てコピーへ移送した。
既存 prefix が保持され、移送前後で native 検証結果が一致することを確認した。
CHANGE-9998 / 9999 の生成物は本番に取り込まない。
この canary の提案時点では本番の CHANGE-043 は未実行だった。
canary を本番の実行根拠の代わりには使わない。

材料系の 4 テストは、古い cycle の REQ-AIMS-002 ではなく、
現在の注釈にある REQ-AIMS-003 / 004 / 010 に対応することを確認した。
静的チェックと直接検証の 2 テストは現在版で成功し、
続く全体の pytest でも 865 件が成功した。スキップはない。
TEST-AISCI-024 の例外を提案した時点では、要求改訂は承認済みだったが、
設計改訂と実際の archive の個別承認・実行はまだ完了していなかった。
この 865 件の全体実行は CHANGE-044 の schema 修正前の結果である。
修正後は関連 3 テストと実際の native schema の受理・拒否を確認した。
全体 gate については、この修正後の合格をまだ確認していない。

TEST-AIDS-340 の例外を提案する現在は、TEST-AISCI-024 の退役は検証済み。
本番の隔離再現は説明可能性と感度分析の 14 組で成功した後、
TEST-AIDS-340 の修正前テスト成功により停止した。

追加例外の要求改訂は承認済みで、設計改訂を提案中である。
TEST-AIDS-340 の archive は個別承認前であり、実施していない。

履歴 scope の追補を提案する現在、TEST-AIDS-340 の退役は個別承認後に
正規 CLI で実施し、全 610 サイクルの元の内容を保持した。
新しい隔離コピーでは 30 組の正規 Red / Green が成功し、

残る履歴診断には当初の 34 scope に加えて 27 scope があり、
現在の正規 CLI が許す順序移行の code も 1 件含まれる。
現行 TDD が成功しても、過去の CHANGE で順序を証明したとは扱わない。
候補を承認済み要求の正確な 61 scope に限定し、個別承認後にだけ記録する。
同じ code でも許可外 scope は拒否する。

完了後の正当な追補を扱うため、元の移送 manifest と receipt は固定したまま、
新しい追補 manifest に承認 hash、実際の変更段階と Red / Green、
最終 hash と全履歴の保持を結び付ける。
元の再現対象・実行条件・policy は変えない。
未承認の差分や根拠不足を決定的な検証用関数で拒否する。
準備判定は実ファイルを指定する context からこの検証を直接呼び、
完了を自己申告する report は受理しない。
元の移送の期待 hash と transaction ID は呼び出し側で独立して固定する。
記録の検証には native の chain・hash link・各 validator を用いるが、
それだけで生成 process の独立した身元証明を得たとは主張しない。
元の入力 hash の付け替え、停止したコピーの再取り込み、
新しい TDD があるという理由だけの履歴 waiver は採用しない。
本追補提案時点では要求改訂は承認済みで、設計改訂を提案中である。
CHANGE-045 の実装・Red / Green、61 scope の個別操作は未実施である。

### CHANGE-045 の初回実装後に確認した記録不整合

初回実装では 2 件の正規 Red / Green を記録した。
公開 API の戻り値の誤解も回帰テストで再現し、REQ-003 の追加バッチで修正した。
修正後の全体 gate では 865 テストと全 643 TDD サイクルが合格した。
ただし初回の change Red / Green 間に、担当 agent が補助関数の lint 修正を行っていた。
native のファイル単位照合が CHANGE_TEST_CHANGED_AFTER_RED を検出した。
この不整合は、後続バッチや成功したテストで消えたとは扱わない。

実際の tool の patch 記録と Ruff から初回ファイルを再構成した。
両方の native tests fingerprint が元の Red / Green 段階と一致し、
全 test 関数の AST は同一、差分は補助関数の辞書値取得の 2 行だけだった。
根拠 JSON の SHA-256 は
`245e074ddcab3c8193bc03fe756d262ad92459948c5ebe56b0338599aa8cc18b`。
再構成は当時の保存物でも、native TDD の代替根拠でもない。

元の段階記録の改変、過去 61 scope の許可の流用、診断の黙殺は採用しない。
要件で指定した CHANGE-045 の 1 scope だけを別に扱い、抽出時と最終検証で根拠を照合する。
正常な根拠での受理は TEST-GATE-RECOVERY-002 と REQ-002 の新しい単独バッチで検証する。
この限定例外の要求改訂は承認済みで、設計改訂を提案中である。
61 scope と本件の waiver 操作は、いずれも未承認・未実施である。

### 実環境の trace 比較で確認した不一致

上記の提案後、REQ-002 の正規バッチと Quality の追記を完了した。
全体 gate は 865 テストと 644 TDD サイクルが合格した。
元の記録不整合は保持されているが、現在の CHANGE-045 の error 診断は解消した。
この 1 件の waiver は記録せず、別に承認された履歴 61 scope だけを正規 CLI で記録した。
change-history と change-completeness の公開 validator は合格した。

続く実環境の追補検証は、CLI が整列して保存する trace と、
公開 readonly API が探索順で返す trace を不一致と判定した。
node / edge / 診断の要素は同じで、比較処理が順序の違いを考慮していなかった。
公開 `api.canonicalSort` を比較用メモリ内で使い、この誤判定を修正する。
保存済み trace の再配列、独自の比較器、意味内容の検査の省略は採用しない。
除外する時刻は graph 最上位の generatedAt だけとし、内部の同名 field は検査する。

完了済みの CHANGE-045 を再記録せず、REQ-GATE-RECOVERY-003 の修正を CHANGE-046 に残す。
このため本変更の文書だけを手動入力の許可に追加し、全 7 段階を追補へ結び付ける。
共有する実装と test ファイルの現在値は、native order が最後の Green と照合する。
各過去サイクルの Red / Green 同一性と report の根拠も保持する。
新しい未完了 Red や根拠不足がある場合は準備完了を拒否する。
追加の仕様承認と真正な回帰テストが必要になるが、履歴の書き換えは避けられる。
