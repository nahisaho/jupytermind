# ADR-0007: Local nbconvert-based export outside the Jupyter MCP path

## Context / 背景
REQ-AIDS-025/033 require exporting the project notebook to PDF/HTML/slide
form. A rubber-duck review flagged that REQ-AIDS-003 ("all analysis code
execution" goes through the Jupyter MCP tools) and an export requirement
conflict unless the export mechanism's boundary is explicit: export must
not become a hidden second code-execution path.

## Decision / 決定
Perform export with a locally configured, read-only conversion tool
(`nbconvert`, invoked as a local subprocess/library call) operating only on
the already-executed, already-saved notebook JSON. The converter never
re-executes any cell and never calls the Jupyter MCP server; it only reads
`projects/<project_name>/notebooks/<project_name>.ipynb` and writes to
`projects/<project_name>/reports/<name>`.

## Rejected alternatives / 却下した代替案
- Re-running the notebook through Jupyter MCP before export (e.g.
  "papermill"-style re-execution): rejected because it would silently
  re-execute analysis code outside the single MCP-routed request/response
  cycle REQ-AIDS-003 and REQ-AIDS-030/031 reason about, doubling the
  execution-failure surface for a purely presentational operation.
- A browser-automation/headless-print based exporter: rejected as an
  unnecessary, heavier dependency when `nbconvert` already covers
  PDF/HTML/slide export directly from notebook JSON.

## Consequences / 結果
The Report Export component (DES-AIDS-024) must be testable by asserting
zero additional Jupyter MCP execution calls occur during export
(REQ-AIDS-033's acceptance criterion), which requires the export function to
take no MCP client dependency at all.
