# ADR-0104: Scope row_limit truncation to remote (api/database) sources only, never local csv/excel, via a source-kind check at truncation time (DES-AIDS-005)

## Context / 背景
`DES-AIDS-005` (REQ-AIDS-014, REQ-AIDS-032) requires `ingest` to load
CSV/Excel/database/API sources into a dataframe, enforcing a network
allowlist before any remote call and a row-count limit afterward.
REQ-AIDS-032 frames the row limit as a *remote-source safety control*
("bounds downstream processing" after a database/API fetch), not a general
ingestion cap. The original implementation applied `row_limit` truncation
unconditionally to the loaded dataframe regardless of `source_spec.kind`,
which silently truncated local CSV/Excel files too — a defect (GitHub #57):
a user loading a large local CSV would get a silently-truncated dataframe
with no indication the file wasn't fully loaded, even though REQ-AIDS-032
never intended the limit to apply to local sources at all.

## Decision / 決定
Gate the truncation decision on `source_spec.kind` at the single point
where `row_limit` is applied, after the dataframe has already been fully
loaded by the kind-specific branch (csv/excel/api/database): `truncated =
source_spec.kind in _REMOTE_KINDS and len(dataframe) > row_limit`, where
`_REMOTE_KINDS = ("api", "database")`. Only when `truncated` is `True` is
the dataframe sliced via `dataframe.iloc[:row_limit]`; a local `csv`/
`excel` source is always loaded and returned in full, however many rows it
has, with `IngestionResult.truncated` reporting `False`. This keeps the
loading logic (which already differs per `kind`) and the post-load safety
limit as two independent concerns: every `kind` branch loads its full
source first, and only the remote kinds are subject to the row-count
safety bound applied afterward.

## Rejected alternatives / 却下した代替案
- Short-circuiting local-source loading itself with a row cap (e.g.
  `pd.read_csv(..., nrows=row_limit)`): rejected because it would silently
  drop rows from a local file with no `truncated=True` signal distinct from
  "the file genuinely only had that many rows," and because REQ-AIDS-032
  explicitly scopes the limit to the remote-fetch path, not local file
  reads.
- Making `row_limit` a `_REMOTE_KINDS`-only parameter (rejecting it or
  ignoring it entirely for local calls at the API boundary) instead of a
  per-kind truncation check: rejected as unnecessary API surface change —
  the existing single `row_limit` parameter with kind-gated truncation
  achieves the same outcome (local sources unaffected) without forcing
  every caller to reason about which parameter applies to which `kind`.

## Consequences / 結果
A local CSV/Excel source is never truncated by `row_limit`, no matter how
many rows it has — `IngestionResult.truncated` is always `False` for
`kind in ("csv", "excel")`. Only `api`/`database` sources are ever
truncated, and only when the fetched dataframe exceeds `row_limit` after
the fetch completes (the limit never bounds the remote transfer/fetch
itself, only the resulting in-memory dataframe). A newly implemented
ingestion `kind` is not subject to `row_limit` unless it is explicitly
added to `_REMOTE_KINDS`; an unrecognized `kind` is rejected outright with
`ValueError` before truncation is ever considered, so this scoping only
governs the four currently-supported kinds, not an implicit default for
hypothetical future ones.
