# ADR-0101: Build the shared fold plan once in `tune_or_compare` and pass it to every candidate as `cv_splits`, rather than re-deriving it per candidate (DES-AIDS-064)

## Context / 背景
`DES-AIDS-064` (REQ-AIDS-076) requires every hyperparameter/model candidate
within one `tune_or_compare` invocation to be evaluated on the exact same
fold plan, so candidate metrics are directly comparable. `StratifiedKFold`/
`KFold` shuffle before splitting (both instantiated with `shuffle=True` and
the same `random_state`); `GroupKFold` does not shuffle at all, its fold
assignment instead depends entirely on group identity. Calling
`build_cv_splits` independently per candidate, even with the same
`random_state`/arguments, would be a redundant, error-prone way to achieve
plan reuse, and any divergence (e.g. a future change passing a different
`n_splits`/`groups` per candidate by mistake) would silently make
candidates incomparable.

## Decision / 決定
Call `build_cv_splits` exactly once per `tune_or_compare` invocation, before
iterating `grid`, producing `shared_cv_splits`. Pass `shared_cv_splits` as
the `cv_splits=` argument to `train_model` for every candidate, regardless
of the original `cv_strategy`/`cv_splits` arguments `tune_or_compare`
itself received. Because `build_cv_splits` already treats a non-`None`
`cv_splits` argument as authoritative and returns it immediately after
validation (`DES-AIDS-062`/`ADR-0099`), every candidate's internal
`train_model` call re-validates (cheap, idempotent) but never re-generates
the plan — guaranteeing byte-identical fold membership across every
candidate without relying on splitter-level determinism. Candidate ordering
in `all_candidates` follows `grid`'s own list order (a plain `for params in
grid` loop building a list), so it is not affected by dictionary iteration
order.
## Rejected alternatives / 却下した代替案
- Re-calling `build_cv_splits` independently per candidate with the same
  `cv_strategy`/`n_splits`/`random_state`: rejected because it depends on
  the splitter's shuffling being deterministic for identical arguments
  (true today, but an incidental property rather than a guaranteed
  contract) and provides no benefit over building the plan once, while
  adding a theoretical divergence risk if any candidate-specific argument
  were ever threaded into the per-candidate call by mistake.
- Threading `shared_cv_splits` through `grid` as part of each candidate's
  own parameter dict instead of as a separate `cv_splits=` argument to
  `train_model`: rejected because `grid` entries are hyperparameter/model
  descriptors already forwarded as `**params_copy` to `train_model`'s
  model-construction parameters; mixing the fold plan into that same dict
  would conflate model hyperparameters with evaluation-protocol state.

## Consequences / 結果
Every candidate in one `tune_or_compare` call is guaranteed to share
identical fold membership, making `best_metric` comparisons meaningful
regardless of how many candidates are evaluated. `run_automl`
(`DES-AIDS-065`) follows this same one-build-then-reuse pattern for its own
candidate loop, for the same reason. Any future comparator added to this
module that evaluates multiple candidates against `train_model` should
build the fold plan once and pass it as `cv_splits=`, rather than
re-deriving it per candidate.
