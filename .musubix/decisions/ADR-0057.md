# ADR-0057: Mandatory target_claim field on SensitivityPlan/Result/Report

## Context / 背景
`DES-AIDS-044` (REQ-AIDS-056) governs the `sensitivity` module's bounded
grid-search execution and stability classification. GitHub #59 reported
that a `SensitivityResult`/`SensitivityReport` returned from
`run_sensitivity` carries no record of which scientific or business claim
its metric values were testing. Once a `SensitivityResult` tuple is
detached from the call site that produced it (logged, serialized, passed
to another function, or inspected later in a notebook), there is no way to
recover what the sensitivity analysis was actually checking, which makes
audit trails and downstream reporting ambiguous whenever a session runs
more than one sensitivity sweep.

## Decision / 決定
Add a required `target_claim: str` field to `SensitivityPlan`, and
propagate it verbatim onto every `SensitivityResult` produced by
`run_sensitivity` and onto the aggregate `SensitivityReport`, so the claim
being tested travels with the evidence regardless of how far the result is
later passed around or persisted. `target_claim` is validated eagerly:
blank or whitespace-only values are rejected before any specification
enumeration or `analysis_fn` evaluation begins, so a caller cannot silently
produce unattributable results.

Because `target_claim` is a new required (non-defaulted) field on an
existing public dataclass, this is a breaking constructor change:
`SensitivityPlan` and all direct construction/consumption sites
(`dataclasses.asdict`, tuple conversion, snapshot/schema assertions, or
JSON built from those representations) must be updated to supply or expect
the field explicitly, rather than silently defaulting it to an empty or
placeholder value that would reintroduce the original ambiguity.

## Rejected alternatives / 却下した代替案
- Giving `target_claim` a default value (e.g. `""` or `"unspecified"`):
  rejected because a default would let the original problem persist by
  construction — callers could omit the claim exactly as before and still
  get a result that silently loses its attribution context.
- Storing the claim only on `SensitivityPlan` and not propagating it onto
  `SensitivityResult`/`SensitivityReport`: rejected because results and
  reports are the artifacts that typically outlive and detach from the
  originating `plan` object (logged, serialized, or returned from a
  function boundary), so attribution must travel with them directly.
- A separate out-of-band mapping from result identity to claim text (e.g. a
  dict keyed by a generated run ID): rejected as unnecessary indirection —
  embedding the claim directly on the dataclasses is simpler and keeps the
  attribution inseparable from the data it describes.

## Consequences / 結果
Any future change to `SensitivityPlan`, `SensitivityResult`, or
`SensitivityReport`'s field shape must preserve `target_claim` as a
required, non-empty string, since REQ-AIDS-056's acceptance criteria now
depend on every detached result/report instance still identifying its
tested claim; existing direct construction call sites and shape-based
consumers (`dataclasses.asdict`, tuple conversion, snapshot/schema
assertions) require migration to supply the field. Covered by regression
test `TEST-AIDS-293`.
