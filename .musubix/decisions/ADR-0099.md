# ADR-0099: Normalize caller-supplied `cv_splits` through the same validation path as generated folds, keyed on original index labels (DES-AIDS-062)

## Context / 背景
`DES-AIDS-062` (REQ-AIDS-074) requires `build_cv_splits` to either generate
folds from `StratifiedKFold`/`KFold`/`GroupKFold`, or accept a
caller-supplied fold plan and reuse it verbatim. A caller-supplied
`cv_splits` is untrusted input: it could reference unknown row labels,
leave train/test overlap within a fold, repeat a test label within a fold,
or fail to cover every row exactly once in some fold's test side — any of
which would silently corrupt out-of-fold (OOF) artifacts (REQ-AIDS-075)
later in `train_model`, since OOF predictions are assembled by writing each
fold's test predictions into a single row-indexed series/frame.

## Decision / 決定
Represent every fold plan — generated or caller-supplied — as a list of
`(train_labels, test_labels)` pairs expressed in the dataframe's own index
labels (not positional integers), and validate both generated and
caller-supplied plans through one shared `_validate_cv_splits` function
before `build_cv_splits` returns. Validation checks, per fold: every
referenced label exists in `df.index` (`unknown_labels`), the train and
test sides are disjoint (`overlap`), and the test side has no duplicate
labels (`duplicate_test_labels`); across all folds together, validation
also checks that every row in `df.index` appears in exactly one fold's test
side (`missing_test_labels`/`duplicate_test_coverage` — these two
cross-fold checks report the offending labels but, unlike the three
per-fold checks above, do not name a specific fold number, since the
condition spans the whole plan rather than one fold). Cross-validation
itself is gated on `df.index.is_unique` (`_validate_cv_dataframe_index`),
checked first, so index-label-based validation cannot be fooled by
duplicate labels referring to different physical rows. Each of these five
label-related violations raises `ValueError` naming the offending labels
(and, for the three per-fold checks, the offending fold number); a
caller-supplied empty `cv_splits` list is rejected separately with a plain
`ValueError("cv_splits must not be empty")` that names no label, since
there is no fold or label to report. Either way, the function never
silently proceeds with an empty, corrupted, or partially-covering plan.

## Rejected alternatives / 却下した代替案
- Trusting caller-supplied `cv_splits` verbatim (validating only
  generated folds): rejected because `DES-AIDS-063`'s OOF-assembly
  contract depends on exactly-once test coverage holding for *any* fold
  plan reaching `train_model`, and a caller mistake (overlapping folds, a
  typo'd label) would otherwise silently produce wrong OOF rows instead of
  failing fast.
- Validating/representing folds via positional integer indices instead of
  `df.index` labels: rejected because `train_model`/`tune_or_compare`/
  `run_automl` all slice with `.loc[train_idx]`/`.loc[test_idx]` against the
  original dataframe, and a caller-supplied plan naturally refers to row
  identity (labels), not position; using labels end-to-end avoids a
  label-to-position translation step that would itself need validation.

## Consequences / 結果
Every caller of `build_cv_splits` — direct or via `train_model`/
`tune_or_compare`/`run_automl` — gets identical fold-plan integrity
guarantees regardless of whether the plan was generated or supplied,
simplifying downstream OOF-assembly code in `train_model`, which can assume
exactly-once test coverage without re-checking it. Any future caller-
supplied-plan feature in this module should reuse `_validate_cv_splits`
rather than re-implementing overlap/coverage checks, to keep this
invariant centralized in one place.
