# ADR-0075: Persist lifecycle progress as a project-local JSON phase state machine

## Context / 背景
`DES-AISCI-003` (`REQ-AISCI-004`, `REQ-AISCI-005`, `CHANGE-001`) needs a
durable representation of ai-scientist's eight ordered phases that survives
separate CLI invocations and can advance automatically only to the next
legal phase. The architectural choice is what durable state model to use so
phase progression stays explicit, auditable, and aligned with the evidence
gate in `DES-AISCI-017`.

## Decision / 決定
The authoritative lifecycle store is the project-root JSON file
`.ai_scientist_phase_state.json`, represented in code by the frozen
`PhaseState` dataclass and the fixed `PHASE_ORDER` tuple. `load_phase_state(...)`
materializes an initial state with `research-planning` active, an empty
`completed_phases` list, and the remaining phases listed as incomplete.
`mark_phase_complete(handle, phase)` is the only transition API: it rejects
unknown or non-active phases, calls `validate_completion_evidence(handle, phase)`
before writing, appends the completed phase once, computes `next_active` via
`_next_phase(...)`, and persists the updated state by atomic temp-file rename.

This keeps progression as an explicit state machine rather than an inferred
property of whatever files happen to exist. The stored `active_phase`,
`completed_phases`, and `incomplete_phases` fields make the current lifecycle
legible across invocations and let gate logic reason about predecessor phases
without reconstructing history from artifacts.

**Known limitation**: the atomic temp-file-then-rename write prevents a
crash mid-write from corrupting the JSON file, but it does not provide
cross-process mutual exclusion. Two CLI invocations that read, decide, and
write concurrently can still race and silently overwrite one another's
transition (last-writer-wins), which falls short of `DES-AISCI-003`'s
"read-modify-write safe across separate CLI invocations" constraint in the
presence of genuine concurrent writers. This gap is tracked for a dedicated
follow-up as jupytermind#64 rather than fixed here, since introducing a
cross-process lock is implementation work outside the scope of this ADR's
debt remediation.

## Rejected alternatives / 却下した代替案
- **Deriving the active phase on every run purely from the evidence registry**: rejected — evidence presence alone cannot distinguish "completed earlier phase" from "currently active phase whose evidence has been produced but not yet completed," so it would collapse two different workflow states.
- **Using one sentinel file per phase instead of one structured state document**: rejected — scattered marker files make ordered transitions and override history harder to validate atomically, and they do not provide one precise API-shaped object equivalent to `PhaseState`.
- **Storing lifecycle state in SQLite or another heavier database**: rejected — the state model is a small, single-project record with ordered lists and override history, so JSON plus atomic replace satisfies the durability requirement without introducing migration and connection-management complexity.

## Consequences / 結果
Future lifecycle changes must preserve `mark_phase_complete(...)` as the
controlled transition path and keep the serialized state compatible with
the fixed-order progression model. Covered by the acceptance tests in
`tests/test_ai_scientist_phase_state.py`.
