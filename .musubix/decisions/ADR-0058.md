# ADR-0058: Use pandas/scikit-learn primitives directly for new feature_engineering operations

## Context / 背景
`DES-AIDS-013` (REQ-AIDS-015) governs `engineer_features`, which CHANGE-008
extended with four new operations (`aggregate`, `interaction`,
`missing_flag`, `bin`) beyond the pre-existing `one_hot`/`scale`. Each
operation needed group-wise aggregation, string concatenation,
null-masking, and explicit-edge binning semantics with exact,
reproducible, auditable output (a non-empty `definitions` entry per added
column).

## Decision / 決定
Implement all four new operations directly on top of `pandas`
(`DataFrame.groupby(...).transform(...)` for `aggregate`,
`Series.astype("string")` concatenation for `interaction`,
`Series.isna()` for `missing_flag`, `pandas.cut(..., right=True,
include_lowest=True)` for `bin`) rather than introducing a separate
feature-engineering library or writing custom aggregation/binning
algorithms from scratch. `pandas` is already the project's sole dataframe
abstraction (via `DES-AIDS-004.executeCell`), so every one of these
operations has a direct, well-tested, vectorized primitive already
available with no new dependency.

## Rejected alternatives / 却下した代替案
- **A dedicated feature-engineering library** (e.g. `feature-engine`,
  `category_encoders`): rejected because it would add a new runtime
  dependency for semantics (`groupby.transform`, `cut`, boolean masks,
  string concatenation) that `pandas` already provides exactly, with no
  compatibility or API-shape benefit proportional to the dependency cost.
- **Custom hand-written aggregation/binning algorithms** (e.g. manual
  group-accumulation loops, manual edge-comparison binning): rejected as
  slower, harder to audit for correctness against a well-known reference
  (`pandas.cut`'s documented edge/interval semantics), and more
  error-prone than delegating to pandas's own vectorized, widely-used
  implementations.
- **`numpy`-only implementation bypassing pandas indexing**: rejected
  because it would require manually re-deriving group-alignment and
  null-propagation semantics that `DataFrame.groupby(...).transform(...)`
  already provides correctly and efficiently, for no behavioral gain.

## Consequences / 結果
Any future new `engineer_features` operation should default to a direct
pandas (or, for genuinely statistics-estimating operations per
`DES-AIDS-061`, scikit-learn) primitive before considering a new
dependency, consistent with this decision. `aggregate`'s leakage risk
across train/held-out splits (tracked separately, out of CHANGE-008's
scope) is a direct consequence of `groupby(...).transform(...)` computing
statistics over whatever rows are present in `df`, not a defect in this
choice of primitive. Covered by `tests/test_feature_engineering.py`
(REQ-AIDS-015 acceptance tests for `aggregate`/`interaction`/
`missing_flag`/`bin`).
